If a PNG encoder or datastream converter knows that the image has been displayed satisfactorily using a display system
whose [transfer function](002-2-scope.md#dfn-transfer-function) can be approximated by a power function with exponent display\_exponent, the image
can be marked as having the [gamma value](002-2-scope.md#dfn-gamma-value):



```
gamma = 1/display_exponent
```




<a id="ref-for-dfn-gamma-value-16"></a>

<a id="ref-for-dfn-gamma-value-17"></a>

It is better to write a [gAMA](015-11-3-ancillary-chunks.md#11gAMA) chunk with a value that is approximately correct than to
omit the chunk and force PNG decoders to guess an approximate [gamma value](002-2-scope.md#dfn-gamma-value). If a PNG encoder is unable to infer the
[gamma value](002-2-scope.md#dfn-gamma-value), it is preferable to omit the [gAMA](015-11-3-ancillary-chunks.md#11gAMA) chunk. If a guess has to be made
this should be left to the PNG decoder.

<a id="ref-for-dfn-gamma-11"></a>

[gamma](002-2-scope.md#dfn-gamma) does not apply to alpha samples; alpha is always represented linearly.

See also [13.13 Decoder gamma handling](029-13-13-decoder-gamma-handling.md#13Decoder-gamma-handling).

### 12.2 Encoder color handling

See [C. Gamma and chromaticity](035-c-gamma-and-chromaticity.md#C-GammaAppendix) for references to color issues.

PNG encoders capable of full color management will perform more sophisticated calculations than those described here and
may choose to use the [iCCP](015-11-3-ancillary-chunks.md#11iCCP) chunk. If it is known that the image samples conform to the
sRGB specification [[SRGB](044-g-references.md#bib-srgb "Multimedia systems and equipment - Colour measurement and management - Part 2-1: Colour management - Default RGB colour space - sRGB")], PNG encoders are strongly encouraged to use the [sRGB](016-11-3-2-5-srgb-standard-rgb-color-space.md#srgb-standard-colour-space) chunk.

If it is possible for the encoder to determine the chromaticities of the source display primaries, or to make a strong
guess based on the origin of the image, or the hardware running it, the encoder is strongly encouraged to output the
[cHRM](015-11-3-ancillary-chunks.md#11cHRM) chunk. If this is done, the [gAMA](015-11-3-ancillary-chunks.md#11gAMA) chunk should
also be written; decoders can do little with a [cHRM](015-11-3-ancillary-chunks.md#11cHRM) chunk if the [gAMA](015-11-3-ancillary-chunks.md#11gAMA) chunk is missing.

<a id="ref-for-dfn-white-point-4"></a>

There are a number of recommendations and standards for primaries and [white points](002-2-scope.md#dfn-white-point), some of which are linked to
particular technologies, for example the CCIR 709 standard [[ITU-R-BT.709](044-g-references.md#bib-itu-r-bt.709 "ITU-R BT.709, SERIES BT: BROADCASTING SERVICE (TELEVISION). Parameter values for the HDTV standards for production and international programme exchange")] and the SMPTE-C standard [[SMPTE-170M](044-g-references.md#bib-smpte-170m "Television — Composite Analog Video Signal — NTSC for Studio Applications")].

There are three cases that need to be considered:

1. the encoder is part of the generation system;
2. the source image is captured by a camera or scanner;
3. the PNG datastream was generated by translation from some other format.

In the case of hand-drawn or digitally edited images, it is necessary to determine what monitor they were viewed on when
being produced. Many image editing programs allow the type of monitor being used to be specified. This is often because they
are working in some device-independent space internally. Such programs have enough information to write valid [cHRM](015-11-3-ancillary-chunks.md#11cHRM) and [gAMA](015-11-3-ancillary-chunks.md#11gAMA) chunks, and are strongly encouraged to do so
automatically.

If the encoder is compiled as a portion of a computer image renderer that performs full-spectral rendering, the monitor
values that were used to convert from the internal device-independent color space to RGB should be written into the
[cHRM](015-11-3-ancillary-chunks.md#11cHRM) chunk. Any colors that are outside the gamut of the chosen RGB device should be
mapped to be within the gamut; PNG does not store out-of-gamut colors.

If the computer image renderer performs calculations directly in device-dependent RGB space, a [cHRM](015-11-3-ancillary-chunks.md#11cHRM) chunk should not be written unless the scene description and rendering parameters have been adjusted for a
particular monitor. In that case, the data for that monitor should be used to construct a [cHRM](015-11-3-ancillary-chunks.md#11cHRM) chunk.

A few image formats store calibration information, which can be used to fill in the [cHRM](015-11-3-ancillary-chunks.md#11cHRM) chunk. For example, TIFF 6.0 files [[TIFF-6.0](045-g-2-informative-references.md#bib-tiff-6.0 "TIFF Revision 6.0")] can optionally store calibration information, which if
present should be used to construct the [cHRM](015-11-3-ancillary-chunks.md#11cHRM) chunk.

<a id="ref-for-dfn-gamma-12"></a>

It is **not** recommended that datastream format converters attempt to convert supplied images to a different
RGB color space. The data should be stored in the PNG datastream without conversion, and the source primary chromaticities
should be recorded if they are known. Color space transformation at datastream conversion time is a bad idea because of
gamut mismatches and rounding errors. As with [gamma](002-2-scope.md#dfn-gamma) conversions, it is better to store the data losslessly and incur
at most one conversion when the image is finally displayed.

See [13.14 Decoder color handling](030-13-14-decoder-color-handling.md#13Decoder-colour-handling).
