### 1.4 Terminology

The terminology used to describe XML Schema Datatypes is defined in the
body of this specification. The terms defined in the following list are
used in building those definitions and in describing the actions of a
datatype processor:

<a id="dt-compatibility"></a>

[Definition:] for compatibility
:   A feature of this specification included solely to ensure that schemas
    which use this feature remain compatible with [[XML 1.0 (Second Edition)]](044-h-references.md#XML)

<a id="dt-may"></a>

[Definition:]**may**
:   Conforming documents and processors are permitted to but need
    not behave as described.

<a id="dt-match"></a>

[Definition:]**match**
:   (Of strings or names:) Two strings or names being compared must be
    identical. Characters with multiple possible representations in ISO/IEC 10646 (e.g.
    characters with both precomposed and base+diacritic forms) match only if they have
    the same representation in both strings. No case folding is performed. (Of strings and
    rules in the grammar:) A string matches a grammatical production if it belongs to the
    language generated by that production.

<a id="dt-must"></a>

[Definition:]**must**
:   Conforming documents and processors are required to behave as
    described; otherwise they are in [·error·](003-1-4-terminology.md#dt-error).

<a id="dt-error"></a>

[Definition:]**error**
:   A violation of the rules of this specification; results are undefined.
    Conforming software [·may·](003-1-4-terminology.md#dt-may) detect and report an
    **error** and [·may·](003-1-4-terminology.md#dt-may) recover from it.

<a id="constraints-and-contributions"></a>

### 1.5 Constraints and Contributions

This specification provides three different kinds of normative
statements about schema components, their representations in XML and
their contribution to the schema-validation of information items:

<a id="dt-cos"></a>

[Definition:] **Constraint on Schemas**
:   Constraints on the schema components themselves, i.e. conditions
    components [·must·](003-1-4-terminology.md#dt-must) satisfy to be components at all.
    Largely to be found in [Datatype components (§4)](018-4-datatype-components.md#datatype-components).

<a id="dt-src"></a>

[Definition:] **Schema Representation Constraint**
:   Constraints on the representation of schema components in XML. Some but
    not all of these are expressed in [Schema for Datatype Definitions (normative) (§A)](033-5-conformance.md#schema) and
    [DTD for Datatype Definitions (non-normative) (§B)](035-b-dtd-for-datatype-definitions-non-normative.md#dtd-for-datatypeDefs).

<a id="dt-cvc"></a>

[Definition:] **Validation Rule**
:   Constraints expressed by schema components which information
    items [·must·](003-1-4-terminology.md#dt-must) satisfy to be schema-valid. Largely
    to be found in [Datatype components (§4)](018-4-datatype-components.md#datatype-components).

## 2 Type System

This section describes the conceptual framework behind the type system
defined in this specification. The framework has been influenced by the
[[ISO 11404]](044-h-references.md#ISO11404) standard on language-independent datatypes as
well as the datatypes for [[SQL]](044-h-references.md#SQL) and for programming
languages such as Java.

The datatypes discussed in this specification are computer
representations of well known abstract concepts such as
*integer* and *date*. It is not the place of this
specification to define these abstract concepts; many other publications
provide excellent definitions.

<a id="datatype"></a>

### 2.1 Datatype

<a id="dt-datatype"></a>

[Definition:]In this specification,
a **datatype** is a 3-tuple, consisting of
a) a set of distinct values, called its [·value space·](003-1-4-terminology.md#dt-value-space),
b) a set of lexical representations, called its
[·lexical space·](004-2-3-lexical-space.md#dt-lexical-space), and c) a set of [·facet·](004-2-3-lexical-space.md#dt-facet)s
that characterize properties of the [·value space·](003-1-4-terminology.md#dt-value-space),
individual values or lexical items.

<a id="value-space"></a>

### 2.2 Value space

<a id="dt-value-space"></a>

[Definition:]A **value
space** is the set of values for a given datatype.
Each value in the **value space** of a datatype is denoted by
one or more literals in its [·lexical space·](004-2-3-lexical-space.md#dt-lexical-space).

The [·value space·](003-1-4-terminology.md#dt-value-space) of a given datatype can
be defined in one of the following ways:

- defined axiomatically from fundamental notions (intensional definition)
  [see [·primitive·](005-2-5-1-3-union-datatypes.md#dt-primitive)]
- enumerated outright (extensional definition)
  [see [·enumeration·](027-4-3-4-3-constraints-on-xml-representation-of-pattern.md#dt-enumeration)]
- defined by restricting the [·value space·](003-1-4-terminology.md#dt-value-space) of
  an already defined datatype to a particular subset with a given set
  of properties [see [·derived·](005-2-5-1-3-union-datatypes.md#dt-derived)]
- defined as a combination of values from one or more already defined
  [·value space·](003-1-4-terminology.md#dt-value-space)(s) by a specific construction procedure
  [see [·list·](004-2-3-lexical-space.md#dt-list) and [·union·](004-2-3-lexical-space.md#dt-union)]

[·value space·](003-1-4-terminology.md#dt-value-space)s have certain properties. For example,
they always have the property of [·cardinality·](023-4-2-3-bounded.md#dt-cardinality),
some definition of *equality*
and might be [·ordered·](022-4-1-6-simple-type-definition-for-anysimpletype.md#dt-ordered), by which individual
values within the [·value space·](003-1-4-terminology.md#dt-value-space) can be compared to
one another. The properties of [·value space·](003-1-4-terminology.md#dt-value-space)s that
are recognized by this specification are defined in
[Fundamental facets (§2.4.1)](004-2-3-lexical-space.md#fundamental-facets).
